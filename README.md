# Домашнее задание к занятию «Микросервисы: подходы»

Вы работаете в крупной компании, которая строит систему на основе микросервисной архитектуры.
Вам как DevOps-специалисту необходимо выдвинуть предложение по организации инфраструктуры для разработки и эксплуатации.


## Задача 1: Обеспечить разработку

Предложите решение для обеспечения процесса разработки: хранение исходного кода, непрерывная интеграция и непрерывная поставка. 
Решение может состоять из одного или нескольких программных продуктов и должно описывать способы и принципы их взаимодействия.

Решение должно соответствовать следующим требованиям:
- облачная система;
- система контроля версий Git;
- репозиторий на каждый сервис;
- запуск сборки по событию из системы контроля версий;
- запуск сборки по кнопке с указанием параметров;
- возможность привязать настройки к каждой сборке;
- возможность создания шаблонов для различных конфигураций сборок;
- возможность безопасного хранения секретных данных (пароли, ключи доступа);
- несколько конфигураций для сборки из одного репозитория;
- кастомные шаги при сборке;
- собственные докер-образы для сборки проектов;
- возможность развернуть агентов сборки на собственных серверах;
- возможность параллельного запуска нескольких сборок;
- возможность параллельного запуска тестов.

Обоснуйте свой выбор.

*Для организации разработки предлагаю использовать **облачный GitLab.com с GitLab CI/CD и собственными GitLab Runner**. Для каждого микросервиса создаётся отдельный Git-репозиторий, а процессы сборки, тестирования и развёртывания описываются в файле .gitlab-ci.yml. Сборки запускаются автоматически при изменении кода или вручную через веб-интерфейс с возможностью указания необходимых параметров. Для разных вариантов сборки можно создавать отдельные задания с собственными настройками, использовать общие шаблоны через include и добавлять произвольные команды в этапы выполнения. Пароли и ключи доступа хранятся в защищённых переменных GitLab CI/CD, а сборки выполняются в собственных Docker-образах на GitLab Runner, которые можно разместить на серверах компании. Использование нескольких Runner и параметров parallel и parallel:matrix позволяет одновременно выполнять несколько сборок и тестов, поэтому такое решение подходит для разработки большого количества микросервисов.*


## Задача 2: Логи

Предложите решение для обеспечения сбора и анализа логов сервисов в микросервисной архитектуре.
Решение может состоять из одного или нескольких программных продуктов и должно описывать способы и принципы их взаимодействия.

Решение должно соответствовать следующим требованиям:
- сбор логов в центральное хранилище со всех хостов, обслуживающих систему;
- минимальные требования к приложениям, сбор логов из stdout;
- гарантированная доставка логов до центрального хранилища;
- обеспечение поиска и фильтрации по записям логов;
- обеспечение пользовательского интерфейса с возможностью предоставления доступа разработчикам для поиска по записям логов;
- возможность дать ссылку на сохранённый поиск по записям логов.

Обоснуйте свой выбор.


*Для централизованного сбора логов предлагаю использовать **Fluent Bit, Apache Kafka, Logstash и OpenSearch с веб-интерфейсом OpenSearch Dashboards**. На каждом сервере устанавливается Fluent Bit, который считывает логи контейнеров, записываемые приложениями в stdout, и отправляет их в Kafka. Далее Logstash получает сообщения из Kafka, при необходимости обрабатывает их и сохраняет в OpenSearch. Для обеспечения надёжной доставки настраиваются дисковая буферизация и повторные попытки отправки в Fluent Bit, а также репликация данных в Kafka, что позволяет избежать потери сообщений при временной недоступности центрального хранилища при условии достаточного объёма буферов. Через OpenSearch Dashboards разработчики могут искать и фильтровать записи по времени, названию сервиса, уровню ошибки и другим параметрам с учётом настроенных прав доступа. Поисковые запросы можно сохранять и передавать коллегам по ссылке, а использование Kafka позволяет обрабатывать большие объёмы логов без прямой зависимости приложений от доступности OpenSearch.*

## Задача 3: Мониторинг

Предложите решение для обеспечения сбора и анализа состояния хостов и сервисов в микросервисной архитектуре.
Решение может состоять из одного или нескольких программных продуктов и должно описывать способы и принципы их взаимодействия.

Решение должно соответствовать следующим требованиям:
- сбор метрик со всех хостов, обслуживающих систему;
- сбор метрик состояния ресурсов хостов: CPU, RAM, HDD, Network;
- сбор метрик потребляемых ресурсов для каждого сервиса: CPU, RAM, HDD, Network;
- сбор метрик, специфичных для каждого сервиса;
- пользовательский интерфейс с возможностью делать запросы и агрегировать информацию;
- пользовательский интерфейс с возможностью настраивать различные панели для отслеживания состояния системы.

Обоснуйте свой выбор.


*Для мониторинга инфраструктуры и микросервисов предлагаю использовать **Prometheus, Grafana, Node Exporter и cAdvisor**. На каждом сервере устанавливается Node Exporter, который предоставляет метрики загрузки процессора, использования оперативной памяти, дискового пространства и сетевых интерфейсов. Для контроля ресурсов отдельных микросервисов используется cAdvisor, собирающий данные о потреблении CPU, RAM, дисковых ресурсов и сети контейнерами, а при использовании Kubernetes дополнительно можно получать метрики томов через kubelet. Специфичные для приложений показатели, например количество запросов, ошибки и время ответа, передаются через endpoint /metrics с использованием библиотек Prometheus. Prometheus периодически собирает эти данные и позволяет выполнять запросы и агрегацию метрик с помощью PromQL, а Grafana предоставляет веб-интерфейс для построения графиков и информационных панелей. Такое решение позволяет отслеживать состояние как отдельных сервисов, так и всей инфраструктуры, а также создавать собственные панели мониторинга для разработчиков и администраторов.*
